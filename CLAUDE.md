# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

You should always aim to be the best engineer you can be. Give high quality code and it will pay dividends in the long run. You are a steward of the code!

## Judge the code, don't copy it

Existing patterns in this repo are evidence, not authority. Before reusing one, decide whether it is actually right *for the case in front of you* — and if it isn't, do the better thing and say why. An existing implementation being there is not a reason; it may be a bug nobody has hit yet.

Things that have gone wrong by copying instead of thinking:

- Duplicating a whole HTTP client into a second module because one already existed, instead of extracting the shared layer.
- Carrying a "not transactional — known limitation" caveat forward as if it were a constraint, when the right move was to make the endpoint transactional.
- `db.flush()` inside a loop because the single-object `add → flush → read .id` idiom looked familiar; one flush after `add_all` assigns every primary key.
- `localStorage` for a panel's open/closed state because a neighbouring component did it, where plain `useState` was correct.

The same applies to comments and docs: don't restate a claim from another file without checking it's still true. Write what the code actually does.

## Dev environment

Everything runs in Docker. All commands go through `docker compose -f docker-compose.dev.yml`; Python is not meant to be run on the host. Services: `frontend` (React/Vite, port 5173), `backend` (FastAPI, port 8000), `celery_worker`, `mcp` (MCP server, port 8001), `postgres`, `redis`.

```bash
# First-time build (user IDs matter for the bind mount)
docker compose -f docker-compose.dev.yml build --build-arg USER_ID=$(id -u) --build-arg GROUP_ID=$(id -g)

# Start / stop / logs
docker compose -f docker-compose.dev.yml up -d
docker compose -f docker-compose.dev.yml down
docker compose -f docker-compose.dev.yml logs -f backend        # or celery_worker

# Alembic (always inside the backend container)
docker compose -f docker-compose.dev.yml exec backend alembic revision --autogenerate -m "..."
docker compose -f docker-compose.dev.yml exec backend alembic upgrade head

# Bootstrap the first user (all endpoints except POST /api/auth/login require a JWT)
docker compose -f docker-compose.dev.yml exec backend python -m app.scripts.create_user

# psql shell
docker compose -f docker-compose.dev.yml exec postgres psql -U roster -d roster_engine
```

- The `backend` service (uvicorn, port 8000) auto-reloads on code changes; the `celery_worker` does **not** — run `docker compose -f docker-compose.dev.yml restart celery_worker` after changing solver or task code.
- Swagger UI at http://localhost:8000/docs; health at `/api/health`. The web app is at http://localhost:5173.
- Frontend tests: `docker compose -f docker-compose.dev.yml exec frontend npm test` (vitest). No backend test suite or linter is configured.

### Alembic gotchas (from README)

- Review autogenerated migrations before applying: autogenerate may emit duplicate `op.create_unique_constraint` lines that already exist in a previous migration.
- The initial schema migration's `downgrade()` must `op.execute('DROP TYPE IF EXISTS rosterstatus')` — Postgres enum types are not dropped automatically and orphaned types break re-migration.

## Architecture

Three components: a React frontend (`frontend/`), the backend (`backend/`), and an MCP server (`backend/app/mcp_server/`, its own container) that exposes roster operations as MCP tools over Streamable HTTP at port 8001, authenticating to the backend with the `svc-mcp` service account and requiring clients to send `MCP_ACCESS_TOKEN` as a bearer header (both in `.env`; see `MCP-guide.md`). An operator-facing manual lives at `documentation/operators-manual.html`.

The frontend (React 18 + Vite + TypeScript, react-query, react-router) talks to the API via the Vite dev proxy (`VITE_PROXY_TARGET`). Pages live in `frontend/src/pages/`, one per nav item.

Two deliberately separated layers under `backend/`:

- **`solver/`** — a pure, DB-agnostic roster engine built on OR-Tools CP-SAT. `solver/models.py` defines plain dataclasses (`Shift`, `ShiftGroup`, `Staff`, `Skill`, `Demand`); `solver/solver.py` defines `RosterEngine.generate_roster()`. It knows nothing about FastAPI, SQLAlchemy, or Celery. Keep it that way.
- **`app/`** — FastAPI app: `models/` (SQLAlchemy ORM), `schemas/` (Pydantic), `routers/` (all mounted under `/api`), `dependencies/auth.py` (JWT), `worker/` (Celery).

The bridge between them is `app/worker/tasks.py`:
- `_build_solver_inputs()` translates DB rows into solver dataclasses (a `Profile` selects which shifts and staff participate; staff with no `permitted_shifts` rows are permitted all shifts).
- `_result_to_json()` / `_json_to_result()` round-trip the solver's tuple-keyed result dict to/from the JSONB stored in `roster.result` — both must be updated together when the result shape changes.

### Roster lifecycle

`POST /api/rosters` creates a `Roster` with `status=running` and dispatches the `run_solver` Celery task; clients poll `GET /api/rosters/{id}`. The task sets status to `draft` (solution found) or `failed` (infeasible or exception, error stored in `result`). Draft rosters are then approved or discarded via dedicated endpoints — status transitions are enforced in `routers/rosters.py`.

### Profile as the configuration unit

A `Profile` groups the staff + shifts eligible for a roster and carries a `config` JSONB with solver settings: objective weights (`weight_consec`, `weight_overstaff`, `weight_burden`, `weight_night`, `weight_weekend`), `time_limit`, and `conditional_constraints` (serialized `ConditionalConstraint` rules — dynamic if/then rules like "block all shifts the day after a night shift").

### Roster chaining

Passing `previous_roster_id` when creating a roster rebuilds the previous result and derives a `RosterContext` (consecutive-working-day counts, each staff member's most recent shift group, overnight shifts on the last day). The solver uses it to enforce rest rules and demand coverage **across the roster boundary** — e.g. a carried-over night shift counts toward day-0 early-morning coverage.

### Solver conventions

- All times are **minutes from midnight** (`start_min`/`end_min` in the DB, `start_time`/`end_time` in the solver). Overnight shifts are encoded as `end_time <= start_time` and handled explicitly throughout (coverage checks, timetable rendering, carryover).
- Constraints in `generate_roster()` are numbered C1–C7 in comments; refer to them by number when discussing changes.
- Leaves are not a constraint of their own — they become pre-assignments of each leave's `shift_code` (default `"AL"`) via `build_pre_assignments_for_leaves()`. The referenced shift code must exist among the profile's shifts or the solve fails.
- Demand coverage (C3) is enforced only at boundary "check points" (demand start plus shift starts/ends inside the window), not continuously.
