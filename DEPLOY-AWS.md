# Deploying roster-engine on AWS (ECS Fargate)

Companion to `DEPLOY.md` (Helm / PCAI). Everything AWS-side is Terraform under
`infra/aws/`, in two root modules with separate state:

- `infra/aws/registry/` — the ECR repositories. Long-lived; images survive
  a teardown of the stack.
- `infra/aws/` — the stack, one file per phase. Created and destroyed between
  sessions.

`scripts/aws-deploy.sh` builds and pushes images. The full plan with
reasoning lives in the "Roster Engine on AWS" page.

Prerequisites on the machine running this: `aws` CLI logged in to the target
account with a default region, `terraform` >= 1.5, `docker`.

Day to day, two scripts are all you need:

```bash
scripts/aws-up.sh      # create or update everything (asks for "yes")
scripts/aws-down.sh    # delete everything except ECR images, stops billing
```

Everything from phase 3 onward bills by the hour whether or not it is used,
so run `aws-down.sh` at the end of a session. The phases below explain what
`aws-up.sh` builds, in the order the Terraform files are numbered.

## Phase 1 — images in ECR

Creates two private ECR repositories (`roster-backend`, `roster-frontend`) with
immutable tags and a lifecycle policy that keeps the 10 most recent images.
This is its own Terraform root (`infra/aws/registry/`) precisely so that
`aws-down.sh`, which destroys the stack, never deletes the images.

```bash
cd infra/aws/registry
terraform init
terraform plan      # expect: 4 to add (2 repositories + 2 lifecycle policies)
terraform apply

cd ../../..
scripts/aws-deploy.sh   # build both images, tag with git SHA, push
```

Verify:

```bash
aws ecr describe-images --repository-name roster-backend \
  --query 'imageDetails[].imageTags' --output text
```

Notes:
- The backend image is built from the **repo root** (it copies `documentation/`).
- Images are built for the architecture of the machine running the script.
  The ECS task definitions (phase 5) must declare the same one.

## Phase 2 — network

Creates the VPC (`10.0.0.0/16`), two public subnets across two availability
zones, an internet gateway with the default route, and the four security
groups every later phase attaches to. Nothing here has an hourly cost.

```bash
cd infra/aws
terraform plan      # expect: 19 to add
terraform apply
```

Security group intent, as a table (the rules in `02-network.tf` are the source
of truth):

| Group   | Allows in            | From    |
|---------|----------------------|---------|
| `alb`   | 80, 443              | anywhere |
| `app`   | 8080                 | `alb`   |
| `app`   | 8000                 | `app` (task-to-task over Service Connect) |
| `db`    | 5432                 | `app`   |
| `redis` | 6379                 | `app`   |

`alb` and `app` allow all outbound; `db` and `redis` allow none.

Verify: `terraform output vpc_id`, then in the console VPC → Your VPCs → that
VPC → **Resource map**. It should draw two subnets, one route table and one
internet gateway.

## Phase 3 — Postgres and Redis

Creates RDS Postgres 16 (`db.t4g.micro`, 20 GB gp3, 7-day backups) and
ElastiCache Redis 7 (`cache.t4g.micro`, one node), each in a subnet group
spanning both subnets, neither publicly accessible. The database password is
generated by Terraform (`random_password`) and lives only in state.

**From here on the deployment has an hourly cost** (about $0.035/hour for
this pair). `terraform destroy` removes it.

The IAM identity running Terraform needs RDS, ElastiCache and (for phase 4)
SSM permissions. For an IAM user:

```bash
for p in AmazonRDSFullAccess AmazonElastiCacheFullAccess AmazonSSMFullAccess; do
  aws iam attach-user-policy --user-name <user> --policy-arn arn:aws:iam::aws:policy/$p
done
```

```bash
cd infra/aws
terraform init      # picks up the random provider
terraform plan      # expect: 5 to add
terraform apply     # RDS takes 5-10 minutes to become available
```

Verify: `terraform output rds_endpoint redis_endpoint` print hostnames. You
cannot connect from outside the VPC by design; the first real proof is the
backend's migrations succeeding in phase 5.

Learning-deployment settings to flip once real data exists:
`skip_final_snapshot = false`, `deletion_protection = true`.

## Phase 4 — secrets

Writes every value the app reads from the environment into SSM Parameter
Store as SecureStrings under `/roster/`, and creates the ECS **task execution
role** that is allowed to read exactly those parameters. No hourly cost.

| Parameter                         | Source                                   |
|-----------------------------------|------------------------------------------|
| `/roster/DATABASE_URL`            | built from the RDS endpoint + generated password |
| `/roster/CELERY_RESULT_BACKEND`   | same, with the `db+` prefix              |
| `/roster/REDIS_URL`               | built from the ElastiCache endpoint      |
| `/roster/CELERY_BROKER_URL`       | same                                     |
| `/roster/SECRET_KEY`              | generated (`random_password`)            |
| `/roster/ROSTER_SERVICE_PASSWORD` | generated; the svc-mcp user is created with it in phase 5 |
| `/roster/ANTHROPIC_API_KEY`       | only if `-var anthropic_api_key=...` is passed |

The IAM identity running Terraform needs SSM permissions. An IAM user can
carry at most 10 attached managed policies, so if that quota is hit, grant it
inline instead:

```bash
aws iam put-user-policy --user-name <user> --policy-name ssm-parameters \
  --policy-document '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Action":"ssm:*","Resource":"*"}]}'
```

```bash
scripts/aws-up.sh     # phases 2-4 together if the stack is down
```

Verify (the value contains the real RDS hostname and password):

```bash
aws ssm get-parameter --name /roster/DATABASE_URL --with-decryption \
  --query Parameter.Value --output text
```

## Phase 5 — ECS

The application: one cluster, four task definitions and four services
(backend, worker, mcp, frontend), an Application Load Balancer in front of the
frontend, a CloudWatch log group per service, and the task role that lets ECS
Exec open a shell in the backend. Tasks find each other by name through ECS
Service Connect (`backend:8000`, `mcp:8000`), so the images run unchanged.

Cost while up: about $0.10/hour for the tasks plus $0.025/hour for the ALB, on
top of phase 3.

The image tag comes from `infra/aws/image.auto.tfvars`, which
`scripts/aws-deploy.sh` writes after each push. If it is missing, apply stops
with a message saying so.

```bash
scripts/aws-up.sh            # expect 19 to add on top of phases 2-4
terraform -chdir=infra/aws output app_url
```

Wait for all four services to show 1/1 running:

```bash
aws ecs describe-services --cluster roster --services backend worker mcp frontend \
  --query 'services[].{name:serviceName,running:runningCount,desired:desiredCount}' --output table
```

The backend task may restart once or twice while RDS finishes accepting
connections. If it keeps going, read its log group:

```bash
aws logs tail /ecs/roster/backend --since 10m          # AWS CLI v2
aws logs filter-log-events --log-group-name /ecs/roster/backend \
  --query 'events[].message' --output text             # CLI v1
```

### Bootstrap the users

The API has no default login. Create the admin user and the MCP service
account inside the backend task (needs `session-manager-plugin` installed):

```bash
scripts/aws-bootstrap-users.sh '<admin password>'
```

Then open the `app_url`, log in as `admin`, and generate a roster: a solved
roster proves the worker, Redis and Postgres are all wired.

The database is deleted by `aws-down.sh`, so run the bootstrap again after
each `aws-up.sh`.
